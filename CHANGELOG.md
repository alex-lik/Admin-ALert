# Changelog

Все значимые изменения в этом проекте документируются в этом файле.

Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/),
версионирование — [Semantic Versioning](https://semver.org/lang/ru/).

Версия выводится автоматически из [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/):

| Тип коммита | Эффект на версию |
|---|---|
| `fix:` | patch `0.1.0` → `0.1.1` |
| `feat:` | minor `0.1.0` → `0.2.0` |
| `BREAKING CHANGE:` в теле коммита | major `0.1.0` → `1.0.0` |
| `docs:`, `chore:`, `refactor:`, `test:`, `build:`, `ci:` | версия не меняется |
| `!` после типа/скоупа: `feat(api)!: ...` | major |

Релизы делаются вручную: `python tools/release.py bump --type <t>` → коммит →
тег `vX.Y.Z` → push. Автоматических сборок в проекте нет.

## [Unreleased]

### Added
- Сервер: движок эскалации `app/services/escalation.py` (задачи 2.7–2.9) —
  выбор просроченных алертов, адресация шага (текущий / следующий / всем с
  фолбэком, задача 2.11), продвижение `current_step`, планирование следующего
  таймера, истечение по лимитам профиля. Воркер `python -m app.worker`
  подключён к движку. Проверено живьём: событие → проход воркера → шаг 1 в
  истории, алерт в `notifying`.
- Сервер: `python -m app.seed` — четыре профиля (1.2): `warning`,
  `critical`, `critical-vip`, `local-disk`. Идемпотентный, пригоден для
  тестов.
- Сервер: обработка `resolved` (2.6) — входящее событие закрывает алерт и
  гасит таймеры; resolved без истории даёт честный 404, а не выдуманный
  алерт. Плюс ручной `POST /alerts/{id}/resolve` для ложных срабатываний.
- Сервер: лимит откладываний по количеству — не больше 2 раз в час на алерт
  (считается по аудиту, отдельный счётчик не нужен).
- Сервер: `reassign` переоткрывает подтверждённый алерт — чужое подтверждение
  новый владелец не видел. Передача пишется в аудит каналом `reassign`
  (клиентский тип и подпись обновлены).
- Сервер: молчащий телефон push не ждёт — шаг помечается сорванным, следующий
  наступает раньше расписания, эскалация ускоряется в сторону звонка (2.21).
- Сервер: список сортируется как на экране — активные → VIP → критичность →
  время (раньше код сортировал только по времени вопреки документу).

### Fixed
- `python -m app.seed` падал с `MissingGreenlet`: ленивое чтение шагов
  профиля на AsyncSession запрещено. Плюс особая ловушка: у только что
  созданного профиля коллекция шагов не загружена в принципе, поэтому
  чтение идёт только для pre-existing профилей.
- Новый алерт создавался с `next_action_at=None`, и воркер его никогда бы не
  увидел. Первый таймер взводится при приёме; профиль без шагов даёт
  немедленный таймер, и первый проход признаёт такой алерт истёкшим.
- Детальные загрузки читали закэшированный состав шагов из сессии вместо БД
  (`populate_existing=True`): после reassign карточка показывала историю без
  шага передачи. В проде сессии на запрос, но тесты с общей сессией ловили
  враньё — теперь и там факты.
- `ACKED` убран из `TERMINAL_STATES`: подтверждённый алерт переоткрывается
  передачей, он «закрыт, но не терминален». Добавлены переходы
  `ACKED → NOTIFYING` (передача) и `TRIGGERED → EXPIRED` (пустой профиль).
- Сервер: модель данных (задача 1.1) — `Project` (флаг VIP), `Host`, `Check`,
  `Alert`, `Admin`, `Device`, `OnCallShift`, `EscalationProfile` с шагами,
  `AlertStep` как аудит. Миграция `initial schema`, частичный уникальный индекс
  `uq_alerts_active_dedup` (один активный алерт на `dedup_key`, история
  закрытых не конфликтует) — работает и на Postgres, и на SQLite.
- Сервер: настоящий `POST /events` — проект по `X-API-Key`, дедупликация по
  `dedup_key` (счётчик растёт, эскалация не перезапускается), ответ 202
  (задачи 2.3, 2.4). Проверено живьём: повтор даёт тот же `alert_id`,
  `occurrences: 2`, `duplicate: true`.
- Сервер: выбор профиля эскалации — VIP-проект стартует с `critical-vip`
  независимо от severity (задача 2.12).
- Сервер: вход админа `POST /auth/login`, обновление `POST /auth/refresh`,
  `GET /auth/me` (задача 2.2). Токены с уникальным `jti` — без него два входа
  в одну секунду давали бы байт-в-байт одинаковый токен.
- Сервер: устройства — регистрация с идемпотентностью по токену,
  `GET /devices`, удаление, heartbeat и delivery receipt (задачи 2.2, 2.20,
  2.21).
- Сервер: `GET /alerts` со счётчиками для бейджей, `GET /alerts/{id}` с
  историей эскалации, `POST .../ack`, `.../snooze` (лимит 30 минут),
  `.../reassign` (задачи 2.14, 2.15, 2.22). Ack гасит таймер и возвращает,
  что именно остановлено; комментарий админа пишется в аудит одним шагом.
- Сервер: 49 тестов — дедупликация, переходы состояний, вход и токены,
  ack/snooze, устройства. Найдено и исправлено живьём: маршрут ack не
  коммитил транзакцию (ответ `acked`, в базе `triggered`, эскалация бы
  продолжалась) — добавлен регрессионный тест с перечитыванием из БД.

### Fixed
- `Severity` был определён дважды (схема и модель) — сравнение по `is`
  тихо не работало. Остался один, в `app/models/enums.py`.
- Ключ проекта проверяется после валидации тела запроса, а не до: иначе
  источник с неверным payload получал 401 и чинил бы не тот ключ.
- Полноценный интерфейс клиента на expo-router: логин, список алертов,
  карточка алерта с историей эскалации, настройки, диагностика (задача 3.2).
- `client/src/theme/` — дизайн-токены: палитра, отступы, радиусы, типографика,
  цвета состояний. Обоснованы не «на вкус»: тёмная тема основная из-за ночного
  дежурства, насыщенные цвета только у критичного, контраст выше 7:1.
- `client/src/components/ui.tsx` — базовые элементы: текст со шкалой
  типографики, кнопки четырёх вариантов, бейджи состояний, карточка,
  пустое состояние, строка «подпись — значение».
- `client/src/components/AlertCard.tsx` — карточка алерта с цветной полосой
  уровня и таймлайн истории эскалации с исходами каждого шага.
- `client/src/types/alert.ts` — типы предметной области, совпадающие со схемой
  сервера.
- `client/src/api/demoData.ts` — демо-данные, чтобы интерфейс можно было
  разрабатывать до появления сервера; типы те же, что и у реального API.
- Сортировка списка не по времени, а по важности: активные → VIP →
  критичность → время последнего срабатывания.

### Changed
- Точка входа переведена на `expo-router/entry`, как требует проектный
  `AGENTS.md`. Старый `App.tsx` удалён.
- Кнопки в карточке алерта: «Принял» сделана самой крупной точкой экрана,
  «Передать» и «Отложить» — вторичными. Экран читают ночью и в панике.

## [0.2.0] - 2026-10-12

### Added
- Клиент: Expo SDK 57 + React Native 0.86, сборка через development build
  (`expo-dev-client`). Expo Go не подходит — нужны каналы с `bypassDnd`,
  точные будильники и Kotlin-модуль.
- `client/src/notifications/channels.ts` — каналы `warning` / `critical` /
  `critical-vip` с обходом DND, вибрацией, публичной видимостью на lock screen;
  категории `alarm`/`call` и `fullScreenAction`; локальная эскалация через
  `setAlarmClock` с шагами 1/2/3 мин и отменой при ack (задачи 3.6–3.8, 3.10).
- `client/src/notifications/fcm.ts` — получение FCM-токена, `onTokenRefresh`,
  регистрация устройства на сервере, фоновый обработчик сообщений (3.4).
- `client/App.tsx` — экран диагностики: разрешения, состояние каналов, токен,
  кнопки тестовых алертов (3.13).
- `client/app.json` — разрешения Android из плана (exact alarms, full-screen intent,
  игнорирование оптимизации батареи, foreground service).
- `client/plugins/withNotifeeMavenRepository.js` — config plugin, добавляющий
  maven-репозиторий Notifee при `expo prebuild`. Без него сборка падает с
  `Could not find any matches for app.notifee:core:+`: Android-ядро Notifee
  вкомпоновано в пакет и не лежит ни в Google Maven, ни в Maven Central.
- `make client-check` (типы + `expo-doctor`) и `make android` в корневом `Makefile`.

### Known limitations
- FCM не работает: Firebase-проект ещё не создан (задача 1.7), в `client/`
  лежит placeholder `google-services.json`. Он нужен только чтобы Gradle собрался,
  в репозиторий не коммитится. Экран диагностики честно показывает это в строке
  «FCM-токен».
- У каналов не настроен звук `USAGE_ALARM` (остальная часть задачи 3.7):
  сейчас `sound: 'default'` через `STREAM_NOTIFICATION`. Нужен ресурс в `res/raw`
  и config plugin — вместе с Kotlin-модулем из задачи 3.11.
- `expo-doctor` помечает `@notifee/react-native` как Unmaintained. Оставлено
  осознанно: альтернативы не дают контроля над каналами, `bypassDnd` и
  alarm-потоком, ради которых существует задача 3.7. Помечено исключением.
- `bypassDnd` не проверен: на эмуляторе он всегда `false`, в том числе у каналов
  Google Dialer. Проверяется на реальных устройствах (3.12, 5.3).

### Fixed
- `vibrationPattern` содержал нечётное число элементов, из-за чего Notifee
  отклонял канал и `critical` / `critical-vip` не создавались вообще. Теперь
  чётное число положительных значений. Поймано на устройстве, а не при сборке.
- `asForegroundService: true` в тестовых уведомлениях приводил к тому, что они
  показывались и тут же снимались системой. Флаг перенесён на момент появления
  нативного foreground service (задача 3.11).


## [0.1.0] - 2026-10-12

### Added
- Каркас монорепозитория: `server/` (FastAPI), `client/` (React Native), `desktop-agent/`, `docs/`.
- План проекта перенесён в `docs/plan.md` (5 блоков, чекбоксы) и загружен в Project Visor
  (проект `admin-alert`, 88 задач по разделам плана).
- `docs/architecture.md`: компоненты, жизненный цикл алерта, модель эскалации, исходы звонка.
- SemVer-версионирование: `VERSION`, `CHANGELOG.md`, Conventional Commits.
- `tools/release.py` — релизный инструмент без внешних зависимостей: `show`, `next`, `bump`, `sync`, `validate`.
- Сервер: `/health` и `/health/ready`, `POST /events` с валидацией по единой схеме события
  и ответом 202, автомат состояний алерта с проверкой переходов, каркас воркера на
  опросе `next_action_at`, async-подключение к БД, Alembic.
- `docker-compose.yml`: api, worker, db (postgres), redis.
- `Makefile` с командой `make check` — весь набор проверок вручную, вместо CI.
- Тесты: 15 штук на автомат состояний и HTTP-слой.

### Fixed
- `tools/release.py next`: падал с `TypeError` при разборе диапазона коммитов —
  `BUMP_TYPES | NO_BUMP_TYPES`, где `BUMP_TYPES` — словарь, а не множество.
- `tools/release.py bump`: в индекс попадали только `VERSION` и `CHANGELOG.md`,
  хотя менялись ещё `server/pyproject.toml` и `client/package.json`. Теперь
  индексируются ровно те файлы, которые изменил сам bump.
