# Архитектура Admin-ALert

## Проблема

Пушнуть алерт — не значит довести его до человека. Человек спит, телефон в Doze,
DND включён, Xiaomi съедает фоновые уведомления. Задача системы — **гарантировать
реакцию**, а не доставку сообщения.

Отсюда три принципа, которые пронизывают весь проект:

1. **Дублирование каналов.** Push → Telegram → звонок. Сбой одного канала не
   останавливает эскалацию.
2. **Таймеры в БД, а не в памяти.** Воркер можно перезапускать в любой момент —
   эскалация продолжится с того же шага.
3. **Ack обязателен.** Ценность не в «увидел», а в «отреагировал». Все каналы
   ведут к одному действию — ack, который останавливает машину.

## Жизненный цикл алерта

```
POST /events (firing)
        │
        ├─ dedup_key уже есть и алерт активен? ──► occurrences++ , эскалация НЕ перезапускается
        │
        ▼
   triggered ──► notifying(step 1) ──► notifying(step 2) ──► escalated ──► expired
                      │                    │                    │            │
                      │                    │                    │      лимит повторов
                      ├──── ack ───────────┴────────────────────┘
                      │
                      └─► acked ──(resolved)──► resolved

POST /events (resolved) ──► resolved: таймеры остановлены, «проблема устранена»
```

Допустимые переходы описаны в `server/app/models/enums.py` и покрыты тестами —
всё остальное считается багом.

## Эскалация

Профиль — упорядоченный список шагов (задача 1.2):

| Профиль | Шаги | Особенности |
|---|---|---|
| `warning` | push (+telegram) | уважает тихие часы |
| `critical` | push → telegram → звонок | тихие часы игнорируются |
| `critical-vip` | push ×N → звонок → звонок запасному | стартует с агрессивного профиля |
| `local-disk` | push + локальный экран + звонок | для агента на десктопе |

Шаг адресуется одному из режимов: **текущий дежурный**, **следующий по списку**,
**всем**. Адресат вычисляется в момент выполнения шага, а не при создании алерта —
дежурство могло смениться.

Исход шага (в частности, звонка) определяет следующий шаг:

| Исход звонка | Что делаем |
|---|---|
| ответил + ack | цепочка остановлена |
| ответил без ack | повтор звонка через интервал профиля |
| занято | сразу следующий в списке |
| нет ответа | сразу следующий в списку |
| сбой линии | следующий шаг + запись в аудит |

## Push

- **Android**: data-only сообщение с `high` priority. Приложение само строит
  уведомление в нужном канале. Data-only без high-priority в фоне игнорируется.
- **iOS**: для критичных — `sound` словарём `{critical: 1, name, volume: 1.0}`.
  Требует entitlement `criticalAlert`; фолбэк — Time-Sensitive + звонок.
- **Doze**: high-priority FCM доставляется сразу, обычные откладываются до окна
  обслуживания. Это не «ускорение», а разница между «проснулся» и «не проснулся».
- Delivery receipt от клиента + heartbeat устройства: если телефон давно молчит,
  эскалация идёт на звонок раньше.

### Важность канала: HIGH, а не MAX

Кажущееся «надо бы поставить `MAX`» — ловушка. В Notifee перечисление
`AndroidImportance` заканчивается на `HIGH`, значения `MAX` не существует, и
код с ним просто не скомпилируется. Разница в терминах Android:

- `IMPORTANCE_MAX` (5) — атрибут **отдельного уведомления**;
- `IMPORTANCE_HIGH` (4) — атрибут **канала**, то есть верхняя граница того,
  что вообще можно выставить каналу.

Каналы создаются `AndroidImportance.HIGH`. Этого достаточно, чтобы
`bypassDnd` работал: обход DND действует только при важности не ниже High.

### Каналы создаются один раз

После создания канала важность, звук и обход DND меняет сам пользователь — из
приложения это недоступно. Неверно созданный канал можно «починить» только
удалением у пользователя, а это сносит его настройки. Поэтому конфигурация
каналов задана один раз в `client/src/notifications/channels.ts` и не должна
меняться по ходу разработки.

### Три грабли, найденные при сборке на устройстве

Проверено на Android 17 через `dumpsys notification`, а не по документации.

1. **`vibrationPattern` — чётное число положительных значений.** Нечётный массив
   отклоняется, и канал не создаётся. Ведущий ноль не проходит проверку.
2. **`asForegroundService: true` без foreground service** приводит к тому, что
   уведомление показывается и тут же снимается системой. Флаг включается
   вместе с нативным модулем (3.11), не раньше.
3. **Обход DND нельзя проверить на эмуляторе.** У каналов Google Dialer на
   эмуляторе `mBypassDnd=false`, хотя доступ к политике уведомлений выдан.
   Значит эмулятор годится для проверки «канал создан, уведомление дошло», а
   поведение под DND/Doze/фоном проверяется только на реальных устройствах
   (3.12, 5.3).

## Таймеры

In-memory таймеры не используются. У активного алерта есть `next_action_at` в БД.
Воркер раз в 5–10 секунд:

1. Выбирает алерты с `next_action_at <= now` **с блокировкой строк**
   (`SELECT ... FOR UPDATE SKIP LOCKED` на Postgres) — иначе два воркера
   выполнят один шаг дважды. На SQLite блокировок нет, там один воркер.
2. Выполняет шаг через Dispatcher. Пока каналы не подключены, работает
   NullDispatcher: шаги помечаются `skipped`, а не выдуманным `delivered`.
3. Планирует следующий. После последнего шага — пауза перед `expired`,
   чтобы звонок успел прозвучать.

Три уточнения из реализации:

- Первый таймер взводится при приёме события, а не воркером. Иначе новый
  алерт с `next_action_at = NULL` воркер не увидел бы никогда.
- Push на молчащий телефон (нет свежего heartbeat) помечается сорванным,
  а следующий шаг наступает раньше расписания — эскалация ускоряется
  в сторону звонка.
- Один битый алерт не останавливает проход: ошибка на алерт, rollback,
  дальше по списку.

Следствия: рестарт воркера безопасен, горизонтальное масштабирование — просто
поднять ещё один воркер.
