# Эксплуатация

Всё, что нужно, чтобы система работала не только на dev-машине. Каждая вещь
здесь — с причиной: дежурный должен понимать, что сломается, если её
пропустить, иначе узнает об этом в три часа ночи.

## 1. Готовность: два разных health-check

| Эндпоинт | Что проверяет | Кто спрашивает |
|---|---|---|
| `GET /api/v1/health` | жив ли процесс | балансировщик, оркестратор |
| `GET /api/v1/health/ready` | БД доступна **и** очередь воркера не растёт | балансировщик, watchdog |

Разделение неочевидно и важно. Обычный `/health` показывает только «процесс
не упал». При этом зависший воркер даёт зелёный `/health`: процесс жив, а
пейджинг не идёт. Сообщить об этом некому — некому принимать алерты. Поэтому
очередь входит в **готовность**, и при её росте ответ становится 503.

Если сомневаетесь, что система работает, смотрите в первую очередь сюда:

```bash
curl -s https://alerts.example.com/api/v1/health/ready | jq
# {"status":"ready","database":"ok","backlog":0}
```

`backlog` больше 100 (`WORKER_BACKLOG_ALARM_THRESHOLD`) — эскалация не
успевает, это авария.

## 2. Внешний watchdog

Единственная часть мониторинга, которая не может быть написана внутри
системы: если API лежит, сообщить об этом должен кто-то снаружи.

```bash
# разовая проверка — для cron
python tools/watchdog.py --once

# постоянно
python tools/watchdog.py --interval 30
```

Настройки:

| Переменная | Зачем |
|---|---|
| `TELEGRAM_BOT_TOKEN` | бот, которым отправляется авария |
| `TELEGRAM_ALERT_CHAT_ID` | чат, куда слать (**обязательно**: без него watchdog молча ничего не отправит) |

Код возврата: `0` — порядок, `1` — авария. Повторные сообщения об одной и
той же аварии подавляются на 30 минут, а при смене текста ошибки приходят
сразу — иначе при ночном простое дежурный получил бы сотни одинаковых
сообщений и перестал их открывать.

**Где должен жижать watchdog.** Не в этом же compose: если упадёт Docker или
хост, watchdog упадёт вместе с системой, за которой следит. Отдельная
машина, отдельный контейнер, `systemd`-таймер или внешний сервис
(Uptime Kuma, Healthchecks.io — достаточно любого, кто умеет HTTP GET).

Пример systemd-таймера:

```ini
# /etc/systemd/system/adminalert-watchdog.service
[Service]
Type=oneshot
EnvironmentFile=/etc/adminalert/watchdog.env
ExecStart=/opt/adminalert/tools/watchdog.py --once
```

## 3. Бэкапы

```bash
python tools/backup.py backup          # снять дамп
python tools/backup.py list            # что есть и сколько весит
python tools/backup.py verify backups/adminalert-pg-20261018-030000.sql.gz
python tools/backup.py prune --keep 14 # оставить последние 14
```

**`verify` — не формальность.** Бэкап, который не развернули и не проверили,
не является бэкапом: через полгода выяснится, что последний рабочий дамп —
трёхмесячной давности, а все архивы с тех пор пустые. Команда разворачивает
дамп в отдельную базу и проверяет, что в ней есть алерты.

Расписание (cron, ежечасно + ротация):

```cron
0 * * * * cd /opt/adminalert && python tools/backup.py backup >> /var/log/adminalert-backup.log 2>&1
30 4 * * * cd /opt/adminalert && python tools/backup.py prune --keep 14 && python tools/backup.py verify $(python tools/backup.py list | head -1 | awk '{print $NF}')
```

Дампы содержат хеши паролей админов и токены устройств — доступ к каталогу
`backups/` ограничьте правами (`chmod 700`, владелец — пользователь сервиса).
Копию положите **за пределы хоста**: бэкап на том же диске не переживёт его.

## 4. HTTPS и сетевой периметр

Сейчас compose публикует порт 8080 напрямую (`ports: ["8080:8080"]`). Для
продакшена так оставлять нельзя: `/events` принимает алерты из интернета
по API-ключу, а webhook Telegram принимает нажатия.

Что нужно сделать:

1. **Закрыть прямой доступ к API.** Уберите `ports` у сервиса `api` и
   поставьте перед ним обратный прокси с сертификатом:

   ```yaml
   proxy:
     image: caddy:2-alpine
     ports: ["80:80", "443:443"]
     volumes:
       - ./Caddyfile:/etc/caddy/Caddyfile:ro
       - caddy-data:/data       # сертификаты Let's Encrypt
   ```

   Caddy сам выпускает и перевыпускает сертификат. Конфигурация — две строки,
   весь смысл в отсутствии `ports` у `api`.

2. **Закрыть БД и Redis.** Сейчас у них нет `ports` — и это правильно, не
   добавляйте.

3. **Webhook Telegram** привязывается к `TELEGRAM_WEBHOOK_SECRET`. Без него
   любой, узнав адрес, может подделать нажатие «Принял». Генерируйте
   секрет: `python -c "import secrets; print(secrets.token_urlsafe(32))"`.

4. **Ограничить `/metrics`.** Метрики пока открыты так же, как API. Если
   сборщик Prometheus внутри сети — закройте путь на прокси:

   ```
   @metrics path /api/v1/metrics
   respond @metrics "Not Found" 403
   ```

## 5. Секреты

Сейчас секреты лежат в `.env` рядом с кодом. Для продакшена `.env` — только
на dev-машине.

Что обязано быть в менеджере секретов (Vault, Doppler, 1Password Connect,
Yandex Cloud Lockbox — что используете):

| Переменная | Что это |
|---|---|
| `DATABASE_URL` | включает пароль БД |
| `JWT_SECRET` | подпись токенов; утечка = выпуск токенов админом |
| `FCM_SERVICE_ACCOUNT_FILE` | ключ сервисного аккаунта Firebase: право писать от имени проекта |
| `TELEGRAM_BOT_TOKEN` | право писать от имени бота |
| `TELEGRAM_WEBHOOK_SECRET` | защита webhook от поддельных нажатий |
| `POSTGRES_PASSWORD` | пароль БД в compose |

Правила:

- **`.env` в репозитории быть не должен** — он уже в `.gitignore`, проверьте
  перед первым коммитом в новом окружении;
- ключ Firebase — файл вне репозитория, в compose монтируется томами;
- ротация: `JWT_SECRET` менять нельзя без сброса всех сессий, а вот пароль
  БД и токены ботов — можно и нужно.

## 6. Rate-limit

Ограничение на `/events` по умолчанию — 600 событий в минуту на проект.
Ключ ограничения — **API-ключ проекта**, а не IP: источники стоят за NAT и в
Docker-сетях, где все запросы приходят с одного адреса, и ограничение по IP
отключило бы приём событий целиком.

```bash
# сколько отклонено
curl -s https://alerts.example.com/api/v1/metrics | grep rate_limited
```

Если растёт `adminalert_ratelimit_degraded_total` — Redis недоступен и лимит
считается в памяти процесса. Защита работает, но не общая между инстансами
API: при нескольких репликах реальный лимит умножается на их число. Это
событие требует реакции, поэтому оно и вынесено в отдельную метрику.

## 7. Метрики

`GET /api/v1/metrics`, текстовый формат Prometheus.

| Метрика | Что показывает |
|---|---|
| `adminalert_worker_due` | очередь просроченных алертов — **главная метрика исправности** |
| `adminalert_events_total{status,new}` | приём событий, включая отказы по лимиту |
| `adminalert_steps_total{channel,outcome}` | что реально доставляется по каналам |
| `adminalert_quiet_hours_deferred_total` | сколько алертов ждёт утра |
| `adminalert_ratelimit_degraded_total` | Redis не отвечает, лимит ослаблен |

Нулевой поток `steps_total{outcome="delivered"}` при ненулевом числе шагов
означает, что каналы молчат: FCM-ключ отозван или бот заблокирован.

## 8. Чего пока нет

Честный список, чтобы не искать позже:

- **звонки** (блок 4) — ждут доступа к AMI или HTTP API провайдера;
- **доставка в APNs** — нужен аккаунт Apple и ключ `.p8`;
- **FCM вживую** — нужен реальный Firebase-проект и `google-services.json`;
  до этого шаги честно пишут `skipped`;
- **история алертов в UI клиента** — экран отдаёт демо-данные, подключение
  к API впереди;
- **постоянное хранение сессии клиента** — токен живёт в памяти процесса,
  после перезапуска вход повторяется.
