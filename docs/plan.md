## Короткий ответ

React Native подходит, но критичная часть держится на нативных настройках: каналы Android, критичный звук iOS, полноэкранный режим. Ниже план из 5 блоков с чекбоксами, от решений до продакшена. Реализовывать его удобнее по порядку: сервер с эскалацией, потом клиент, потом звонки.

## Как читать чекбоксы

| Знак | Значит |
|---|---|
| `[ ]` | не начато |
| `[~]` | начато, но не закончено — частично в коде, ждёт блокера или проверки на устройстве |
| `[x]` | сделано и проверено |

Отметки ставятся по факту, а не по плану. Что именно сделано и чем
проверено — в `CHANGELOG.md`, в комментариях Project Visor и в
`client/README.md` / `docs/architecture.md`.

## 2. Сервер

Ядро:
- [x] Каркас проекта, миграции, Docker Compose (api, worker, db).
- [x] Аутентификация админов (токены, refresh), регистрация устройств с FCM/APNs-токеном и платформой.
- [x] Эндпойнт `POST /events` с API-ключом проекта. Валидация, нормализация, ответ 202.
- [x] Дедупликация по `dedup_key`: повторное событие обновляет счётчик и не запускает эскалацию заново.
- [x] Автомат состояний: `triggered → notifying(step N) → acked / escalated / resolved / expired`.
- [x] Обработка `resolved`: остановить таймеры, отправить уведомление «проблема устранена».
- [x] Воркер: выбирает алерты с `next_action_at <= now`, выполняет шаг, планирует следующий.
- [x] Идемпотентность шагов: один шаг не должен выполниться дважды при гонке двух воркеров (блокировка строки, `SELECT ... FOR UPDATE SKIP LOCKED`).
- [x] Ограничение числа повторов и максимум эскалации, чтобы не было бесконечного цикла.

Маршрутизация и люди:
- [ ] On-call расписание: кто основной, кто запасной, смены по времени.
- [x] Шаг эскалации может адресоваться «текущему дежурному», «следующему по списку» или «всем».
- [x] Правила по проекту: VIP-проекты стартуют с более агрессивного профиля.
- [x] Тихие часы только для `warning`. Для `critical` они игнорируются. Окно считается по часовому поясу адресата шага, а не сервера; действует на каждый шаг цепочки, а не только на первый.
- [x] Ack через API: `POST /alerts/{id}/ack`, `snooze` (с жёстким лимитом по времени и количеству), `reassign`.
- [x] Ack синхронизируется: после него останавливаются push-повторы, звонок и Telegram-напоминания.
- [x] Нажатие в Telegram останавливает ту же эскалацию, что и кнопка в приложении: общий сервис, общий аудит.
- [x] On-call расписание: заведение смен, ротация по кругу, кто дежурит сейчас, проверка покрытия. Адресация шага берёт дежурного из расписания, а при его отсутствии или дыре — фолбэк с меткой, по которой видно, что именно сломано.

Доставка push:
- [x] Отправка в FCM с `priority: high`. Для критичных алертов это важно: в Doze обычные сообщения откладываются до окна обслуживания, а high-priority доставляются сразу .
- [x] Для Android слать data-сообщение с высоким приоритетом, чтобы приложение само строил уведомление в нужном канале. Data-only без high-приоритета в фоне игнорируется как низкоприоритетное .
- [~] Отправка в APNs: для критичных формат `sound` как словарь с `critical: 1`, `name` и `volume: 1.0` . Блок APNs собирается, но отправка требует подписи ключом Apple (задачи 1.8, 1.9). `critical: 1` по умолчанию выключен: без entitlement от Apple FCM отвечает BadPriority и уведомление не доходит вовсе.
- [x] Обработка недействительных токенов: удалять устройство при ответе об ошибке.
- [x] Запись факта доставки: приложение шлёт «получено» (delivery receipt) на сервер.
- [x] Heartbeat устройств: если устройство давно не отвечало, сервер переходит на звонок раньше по расписанию.

Операционка:
- [x] Логи шагов эскалации (аудит: кому, когда, каким каналом, результат).
- [x] Метрики и собственный мониторинг: `/metrics` в формате Prometheus, `/health/ready` учитывает очередь воркера (при зависшем воркере `/health` зелёный, а пейджинг стоит), внешний watchdog `tools/watchdog.py` с подавлением повторов. Развёртывание и настройки — `docs/operations.md`.
- [x] Бэкапы БД, rate-limit на `/events` — сделано. Секреты в менеджере и HTTPS — инструкция в `docs/operations.md`, само развёртывание требует доступа к инфраструктуре.

## 4. Звонки и интеграции

SIP через вашу телефонию:
- [ ] Включить AMI в `manager.conf` (по умолчанию TCP 5038), создать отдельного пользователя с минимальными правами и закрыть порт файрволом .
- [ ] Реализовать вызов через `Originate` с таймаутом ожидания ответа и CallerID, который админ узнаёт . Использовать асинхронный режим, чтобы не блокировать воркер.
- [ ] Написать диалплан: приветствие, TTS с описанием («проект X, хост Y, диск заполнен»), меню «1 — принять, 2 — передать дальше, 3 — повторить».
- [ ] Принимать DTMF: события `DTMFBegin`/`DTMFEnd` дают нажатую цифру . Результат сообщать серверу по HTTP из диалплана или через события AMI.
- [ ] Обработать исходы: ответил+ack, ответил без ack, занято, нет ответа, сбой линии. Каждый исход определяет следующий шаг.
- [ ] Клиентская библиотека для Python: `asterisk-ami` или собственная лёгкая реализация .
- [ ] Если телефония не на Asterisk, заменить слой на HTTP API провайдера. Интерфейс `CallProvider` оставить прежним.
